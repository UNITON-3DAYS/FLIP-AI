# FLIP 시스템 아키텍처 / 제품 방향

인식·채점 부분의 시스템 경계와 콘텐츠 트랙 정리.
(인식 모델·학습 세부는 [recognition-pipeline.md](recognition-pipeline.md) 참고.)

---

## 1. 시스템 경계

책 넘김 캡처와 장(page) 분리는 **다른 서버**가 담당한다. 우리는 **페이지 이미지 1장을 입력으로 받는 데서 시작**한다.

```
[다른 서버]  넘김 영상 → 장별 분리 → 페이지 이미지들
                                        │
                                        ▼
[우리]  페이지 이미지 → 보정 → OCR로 문제 블록 절단 → VLM 판독 → 채점 결과
```

| | 담당 |
|---|---|
| 넘김 영상, 모션 감지, 장별 분리 | ❌ 다른 서버 |
| 페이지 이미지 받아 인식·채점 | ✅ 우리 |

→ **모션 감지/자동촬영은 우리 스코프 아님.** 우리 서비스 = **"페이지 이미지 in → 채점 결과 out".**

---

## 2. 콘텐츠 트랙 (2종)

판독(VLM)은 공통. **"문제 블록을 어떻게 찾느냐(앞단)"만** 트랙별로 다르다.

| 트랙 | 설명 | 블록 찾기 | 난이도 |
|---|---|---|---|
| **쎈 등 기성 학습지** (현재) | 기성 출판물 (통제 불가, 표준화됨) | **OCR로 쪽수·문제번호(anchor) 인식 → 블록 절단** (`structure`) | 중 |
| **자체 시험지** (아직 미구현) | 우리가 만듦 (레이아웃 통제 가능) | **ArUco 마커 + 고정좌표 슬라이싱** | 쉬움 |

### 쎈이 가능한 이유
- 쎈은 **표준 출판물** → 쪽수·문제번호가 크고 진한 인쇄체라 OCR이 안정적으로 잡는다.
- DB에 페이지별 문제번호를 등록해두면 anchor 오독을 걸러 블록 경계를 안정적으로 자른다.
- **전제: 학생은 풀이를 섞지 않고, 문제 밑 공간에 답만 적는다.** → 블록을 통째로 VLM에 넘겨도 답 하나만 읽으면 되어 깨끗. (풀이가 심하게 섞이면 보류로 흡수)

---

## 3. 우리 파이프라인 (입력 = 페이지 1장)

```
페이지 이미지
  → 보정(preprocess) → OCR(PaddleOCR)
  → (쎈) 쪽수 인식 + 문제번호 anchor로 문제 블록 절단 (structure)
  → 각 문제 블록을 통째로 크롭 → VLM 판독 (객관식=동그라미 번호 / 주관식=손글씨 값)
  → 정답 비교(집합 일치 / SymPy 동치) → O/X
  → 인식 실패·불확실 → 보류(사람 확인)
```

- **판독(VLM)** = 공통. 구현·실측 검증됨(11~12/12, 오채점 0).
- **앞단(OCR 블록 절단)** = 쎈 트랙 구현됨. 자체 시험지(마커) 트랙은 미구현.

---

## 4. Staging (구현 순서)

1. **쎈** (현재) — OCR anchor로 블록 절단 + VLM 판독. **"사진→블록→VLM→채점" 전체 루프 완성·실측 검증.**
2. **자체 시험지** — 마커+고정좌표 크롭으로 앞단 교체. **판독(VLM)은 그대로 재사용.**
3. (책 넘김 캡처는 다른 서버, 우리 스코프 밖)

판독기가 트랙 공통이라 앞단만 갈아끼우면 됨 → 리스크 낮음.

---

## 5. 열린 질문

- **페이지 ID를 누가 주나?** 서버가 페이지 번호까지 태그해주면 우리는 정렬+크롭만. 안 주면 우리가 페이지번호 OCR로 식별.
- **쎈 답공간 크기·일관성** — 문제 밑 답 공간이 등록 가능한 형태인지 실제 페이지로 확인 필요.
